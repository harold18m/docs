This guide is for **partners**: integrators offering email to **their own customers** with RQE underneath (reseller pattern).

There are **two ways** to structure it, and the decision isn't about schema — it's about who gets access.

## Which one to pick

|                                    | **A — one project, N customers** | **B — one project per customer** |
| ---------------------------------- | -------------------------------- | -------------------------------- |
| Credential                         | your `sk_proj_`                  | `sk_partner_` + one `sk_proj_` per customer |
| Domain and reply domain per customer | yes                            | yes                              |
| Per-customer metrics               | `GET /v1/domain-stats`           | `GET /v1/partner/projects/:id/stats` |
| Per-customer rate limits           | no, project-wide                 | **yes**                          |
| Your customer signs into RQE       | **not possible**                 | **yes**                          |
| What you manage                    | one key                          | N projects and N keys            |

<Tip>
  **Start with A.** Fewer moving parts, and it covers the common case: you own the interface and RQE is the infrastructure underneath.

  Pick **B** if you need any of these three: your end customer signing into the RQE dashboard, per-customer sending limits, or separate credentials so you can revoke just one.
</Tip>

<Info>
  **Already integrated with B?** There's nothing to migrate. The `/v1/partner` endpoints stay supported and your projects work exactly the same. B isn't a deprecated path — it's the right choice when you need what A doesn't offer.
</Info>

## Path A — one project, N customers

Your project, your API key, your customers' domains inside it.

<Steps>
  <Step title="Register your customer's domain">
    With your project's API key, register each customer's domain and get back the DNS records they need to publish.

    ```bash
    curl -X POST https://api.reallyquickemails.com/domains/register \
      -H "Authorization: Bearer sk_proj_xxxxxxxxxxxx" \
      -H "Content-Type: application/json" \
      -d '{ "domain": "customer.com" }'
    ```

    To let them publish DNS in one click, use [Domain Connect](/en/api-reference/domains): `GET /domains/customer.com/domain-connect` returns a signed URL that creates the records at their provider.
  </Step>

  <Step title="Register their reply domain (optional)">
    So replies land at `name@reply.customer.com` instead of a token-encoded address:

    ```bash
    curl -X POST https://api.reallyquickemails.com/domains/reply \
      -H "Authorization: Bearer sk_proj_xxxxxxxxxxxx" \
      -H "Content-Type: application/json" \
      -d '{ "domain": "customer.com" }'
    ```

    **You can register one per customer within the same project.** Each send resolves the reply domain matching the sender's domain. To verify a specific one, pass `domain` in the body of `POST /domains/reply/verify`.
  </Step>

  <Step title="Wait for verification">
    Once your customer publishes the DNS, you get the **`domain.verified`** webhook — no polling needed. See [Webhooks](/en/api-reference/webhooks).
  </Step>

  <Step title="Send on their behalf">
    With the same API key, [send](/en/api-reference/public-api) transactional or batch email using their domain as the sender.
  </Step>

  <Step title="Debug and measure per customer">
    A specific customer's sends:

    ```bash
    curl "https://api.reallyquickemails.com/v1/activity?sender_domain=customer.com&status=bounced" \
      -H "Authorization: Bearer sk_proj_xxxxxxxxxxxx"
    ```

    And their aggregated metrics — deliveries, bounces, opens and clicks:

    ```bash
    curl "https://api.reallyquickemails.com/v1/domain-stats" \
      -H "Authorization: Bearer sk_proj_xxxxxxxxxxxx"
    ```

    See [Activity and domain-stats](/en/api-reference/activity).
  </Step>
</Steps>

<Warning>
  **Watch `hard_bounce_rate`, not the total bounce count.** Providers calculate the suspension threshold (~5%) on **permanent** bounces; transient ones don't count. A domain can show 12% total bounces while staying below 1% hard bounce.

  Also ask each customer to publish **DKIM on their own domain**: that's what makes their sending reputation theirs, rather than blending with everyone else's.
</Warning>

## Path B — one project per customer

Each customer is an independent RQE project, with isolated data, limits and stats. You create and operate them with a **partner key** (`sk_partner_...`), issued by RQE when your partner account is enabled.

<Steps>
  <Step title="Create the customer's project">
    ```bash
    curl -X POST https://api.reallyquickemails.com/v1/partner/projects \
      -H "Authorization: Bearer sk_partner_xxxxxxxxxxxx" \
      -H "Content-Type: application/json" \
      -d '{ "name": "Customer", "external_key": "your-internal-id" }'
    ```

    ```json
    { "project_id": "…", "slug": "customer", "api_key": "sk_proj_…" }
    ```

    Store the `api_key` securely. The `external_key` makes the call **idempotent**: retrying returns the same project instead of duplicating it.
  </Step>

  <Step title="Configure and operate">
    With the customer's `api_key`, the flow is the same as path A: register their domain, their reply domain, and send. All isolated to that project.
  </Step>

  <Step title="Manage your portfolio">
    `GET /v1/partner/projects` lists your customers and `GET /v1/partner/projects/:id/stats` returns each one's metrics.

    From an AI agent, use the [MCP in partner mode](/en/guides/mcp#partner-mode-manage-your-client-portfolio): `list_clients`, `create_client`, `get_client_stats`.
  </Step>
</Steps>
