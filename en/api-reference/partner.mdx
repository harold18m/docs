description: "Create and configure client projects via API with your partner key: authenticated domain, sender, API key and webhook in a single call."
---

If you integrate RQE as a **platform for your own clients** (partner/reseller pattern), these endpoints let you **create and fully configure a client project via API**: its sending domain with the DNS pack, its sender, its API key and its webhook. All with your partner key, without ever holding the client's key.

**Base URL:** `https://api.reallyquickemails.com`

<Info>
  **Each client = one project.** The domain, reply domain, limits and stats are **per project**, so each of your clients is an independent RQE project with its own API key. These endpoints create, configure and list those projects inside **your** partner organization.
</Info>

## Authentication

Partner endpoints use a dedicated **partner key** (distinct from project API keys):

```
Authorization: Bearer sk_partner_xxxxxxxxxxxx
```

The partner key is tied to your organization and can only operate projects **within it**. It's dedicated and revocable without affecting your sends. It's issued by RQE when your partner account is enabled. A missing or invalid key returns `401`. A `projectId` that doesn't belong to your organization returns `404`, never `403`: from the outside, someone else's project is indistinguishable from one that doesn't exist.

<Warning>
  **The partner key does not send email.** It provisions and configures. To send, manage contacts or read a client's activity, use that project's `api_key` (`sk_proj_...`).
</Warning>

## Full onboarding in one call

This is the recommended path. A single `POST` creates the project, registers the sending domain with the complete DNS pack, and creates the sender on that domain.

<Steps>
  <Step title="Create the whole client">
    `POST /v1/partner/projects` with `name`, `domain` and `sender`. You get back `project_id`, `slug`, the client's `api_key`, the DNS records and the public verification link.
  </Step>
  <Step title="Forward the verification link">
    `domain.verification_url` is a public page that shows the records and verifies with one button. Your end client opens it without an RQE account: it's the only thing you need to send them.
  </Step>
  <Step title="Wait for the `domain.verified` webhook">
    Don't poll. RQE re-verifies on its own and notifies you by webhook once DNS propagates. See [Webhooks](/en/api-reference/webhooks#domainverified-domainfailed).
  </Step>
  <Step title="Operate on their behalf">
    With the client's `api_key`, [send](/en/api-reference/public-api), manage [contacts](/en/api-reference/leads) and read activity — all isolated to that project.
  </Step>
</Steps>

## POST /v1/partner/projects

Creates a client project inside your partner organization. The `slug` and `api_key` are generated automatically.

**The only required field is `name`.** `domain` and `sender` are optional and new: if you pass them, onboarding completes in this same call. If you don't, the endpoint responds exactly as before.

<Info>
  **Compatibility: if you already integrated the previous flow, you don't need to change anything.** The call with just `{ "name": "..." }` is still valid and its response did not change. The new fields add to it, they don't replace it.
</Info>

### Request Body

| Field          | Type   | Required | Description                                                                                    |
| -------------- | ------ | -------- | ------------------------------------------------------------------------------------------------ |
| `name`         | string | Yes      | Client name (e.g. `Phrasso`).                                                                    |
| `external_key` | string | No       | Your internal identifier for the client (max 200 characters). Makes the call **idempotent**.     |
| `domain`       | string | No       | **New.** The client's sending domain (e.g. `phrasso.com`). Always travels together with `sender`. |
| `sender`       | object | No       | **New.** `{ "name": "Phrasso", "email": "hello@phrasso.com" }`. Always travels together with `domain`. |
| `webhook_url`  | string | No       | HTTPS webhook URL for the project. If omitted, it inherits your root project's.                  |
| `timezone`     | string | No       | IANA timezone (e.g. `America/Lima`).                                                             |
| `country`      | string | No       | Client's country code.                                                                           |

<Warning>
  **`domain` and `sender` travel together or not at all.** SES won't register a domain without a `From` address, so there's no way to onboard one without the other. If you send only one, the response is `400` **before anything is created**: `SENDER_REQUIRED_FOR_DOMAIN` or `DOMAIN_REQUIRED_FOR_SENDER`. And if the address doesn't end in the domain, `400 SENDER_DOMAIN_MISMATCH`.
</Warning>

### Minimal example — project only

The original flow, unchanged. It creates the project and returns its API key; you configure the domain and the sender afterwards with the endpoints below.

<Tabs><Tab title="cURL">

```bash
curl -X POST https://api.reallyquickemails.com/v1/partner/projects \
  -H "Authorization: Bearer sk_partner_xxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Phrasso" }'
```

</Tab><Tab title="Python">

That `sender` shape — with `id`, `sender_source`, `can_send` and `created_at` — is **the same in all four places** a sender shows up: project creation, domain registration, sender creation and the project detail.

### The DNS pack

`domain.records` carries the full pack, not just DKIM. It's derived entirely in one call.

<Tip>
  **The client publishes `fqdn`, not `name`.** SES-generated records are **relative** to the domain (`_amazonses`, `@`, `_dmarc`, `send`), while the reply and tracking ones are **absolute**. `fqdn` is always the ready-to-paste name, no thinking required; `name` is there so it matches what the [`/domains/*`](/en/api-reference/domains) endpoints show.
</Tip>

| Type    | `purpose`                             | What it's for                                                    |
| ------- | ------------------------------------- | ------------------------------------------------------------------ |
| TXT     | `ses_verification`                    | Proof of domain ownership.                                         |
| CNAME   | `dkim`                                | DKIM signing on the client's domain. There are **3**.              |
| TXT     | `spf`                                 | SPF at the root.                                                   |
| TXT     | `dmarc`                               | Managed DMARC, at `p=none` so reports start flowing.               |
| MX, TXT | `return_path`                         | Custom MAIL FROM on `send.`: bounces and complaints aligned.       |
| CNAME   | `tracking`                            | Click links on `links.`, using the client's own domain.            |
| TXT, MX | `reply_verification`, `reply_inbound` | Clean, token-less Reply-To on `reply.`.                            |

Per-record `status`: `not_set`, `propagating`, `mismatch` or `verified`. The `priority` field appears only on the reply MX; the `send` one carries its priority inside `value`. Details for each record in [Domains](/en/api-reference/domains#generated-dns-records).

<Note>
  **The `records` name belongs only to the endpoints under `/v1/partner`.** The ones under [`/domains/*`](/en/api-reference/domains), called with the client's API key, still return the array as `dns_records`. Nothing changed there.
</Note>

**Reply and tracking are best effort.** If either fails, the domain is still registered and the reason travels in `warnings[]` — onboarding doesn't fall over because of it.

### Idempotency

With `external_key`, retrying the call **returns the same project** instead of duplicating it. It's the field that ties the customer in your system to the RQE project: always use it.

If the `external_key` belongs to a **disabled** client, the response is `409 PROJECT_DISABLED` with the `project_id` in the body, so you know which one to reactivate.

### Partial onboarding

This only applies if you passed `domain` and `sender`. If the project is created but domain registration fails, the response comes back with `partial: true` and the detail in `errors[]`. **The project and its `api_key` are valid**: retry the domain with `POST /v1/partner/projects/{projectId}/domains`.

Every entry in `errors[]` and `warnings[]` is `{ step, error_code, error }`. In `errors[]`, `step` only takes the value `domain`: the sender is created **inside** domain registration, so there's no separate step of its own that can fail. In `warnings[]`, `step` takes `reply_domain`, `tracking_domain` or `verification_link` — the best-effort steps that don't sink the onboarding.

```json
{
  "project_id": "c22e3647-0e4b-4d71-99e2-651dbbac3eb2",
  "slug": "phrasso",
  "api_key": "sk_proj_xxxxxxxxxxxxxxxxxxxxxxxx",
  "partial": true,
  "domain": null,
  "sender": null,
  "errors": [
    { "step": "domain", "error_code": "DOMAIN_SENDER_CONFLICT", "error": "phrasso.com is already tied to another verified sender." }
  ]
}
```

<Note>
  **We never drop a step silently.** If you see neither `partial` nor `warnings` in the response, everything went through.
</Note>

### The `health` block

It's **per project**, not the shape of [`GET /domains/health`](/en/api-reference/domains#get-domainshealth): there's no `summary` and no `data` here.

| Field                   | Description                                                                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| `status`                | `healthy` · `warning` · `critical`, for the whole client.                                      |
| `can_send`              | Whether the client has at least one domain that can send.                                      |
| `dkim_verified`         | Whether DKIM is verified. **That's the field name, not `dkim`** — that one belongs to `by_domain[].auth`. |
| `domains_total`         | Domains registered in the project.                                                             |
| `domains_authenticated` | How many of them are authenticated. The gap between the two is the work left to do.            |
| `sent`                  | Sends in the window (`period_days`).                                                           |
| `hard_bounce_rate`      | The client's hard bounce rate, **weighted by volume** — not the average of the per-domain rates. |
| `issues`                | What's missing, in actionable text. You can forward it to your client as-is.                   |
| `by_domain`             | The usual per-domain health, with `auth: { ses, spf, dmarc, dkim }`.                           |

<Warning>
  **`can_send: true` with `status: critical` is the costliest case.** Mail goes out with a `200` and nothing looks broken, but it ships without DKIM on the client's domain. See [Before you send volume](#before-you-send-volume).
</Warning>

## DELETE /v1/partner/projects/&#123;projectId&#125;

</Tab></Tabs>

**Response** `200 OK`

```json
{ "project_id": "c22e3647-0e4b-4d71-99e2-651dbbac3eb2", "disabled": true }
```

## Client domains

The same domains as `/domains/*`, but with **your partner key** and the client's `projectId` in the path: you don't need each client's `api_key` on hand.

### POST /v1/partner/projects/&#123;projectId&#125;/domains

Registers the client's sending domain, derives the [full DNS pack](#the-dns-pack) and creates the public verification link.

| Field          | Type   | Required | Description                                                        |
| -------------- | ------ | -------- | -------------------------------------------------------------------- |
| `domain`       | string | Yes      | The client's domain (e.g. `phrasso.com`).                           |
| `sender`       | object | Yes      | `{ "name": "Phrasso", "email": "hello@phrasso.com" }`. The address must end in the domain. |
| `external_key` | string | No       | Your internal identifier for the domain.                            |

<Warning>
  **The sender is required and nested under `sender`**, not passed as loose `sender_name` and `sender_email`. SES won't register a domain without a `From` address, so there's no bare domain registration.
</Warning>

<Tabs><Tab title="cURL">


```json
  "identity_id": "8a1f6e2c-3b4d-4f5a-9c6e-7d8f9a0b1c2d",
```

### POST /v1/partner/projects/&#123;projectId&#125;/senders

Creates a sender. **By default it requires a verified domain**: that's the rule that keeps a client from being born sending unauthenticated.

| Field                   | Type    | Required | Description                                                                        |
| ----------------------- | ------- | -------- | ------------------------------------------------------------------------------------ |
| `name`                  | string  | Yes      | Sender display name.                                                                 |
| `email`                 | string  | Yes      | Sender address.                                                                      |
| `external_key`          | string  | No       | Your internal identifier for the sender.                                             |
| `allow_unauthenticated` | boolean | No       | `true` to allow email verification (magic link) when the domain isn't verified. Defaults to `false`. |

`name` and `email` are accepted **loose in the body or nested under `sender`**: both forms work.

<Tabs><Tab title="cURL">

```bash
curl -X POST https://api.reallyquickemails.com/v1/partner/projects/c22e3647-0e4b-4d71-99e2-651dbbac3eb2/senders \
  -H "Authorization: Bearer sk_partner_xxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Phrasso", "email": "hello@phrasso.com" }'
```

</Tab></Tabs>

**Response** `201 Created`

```json
{
  "sender": {
    "id": "123e4567-e89b-12d3-a456-426614174000",
    "from_name": "Phrasso",
    "from_email": "hello@phrasso.com",
    "sender_source": "manual",
    "domain_authenticated": true,
    "email_verified": true,
    "can_send": true,
    "external_key": null,
    "created_at": "2026-07-22T16:00:00.000Z"
  },
  "path": "domain",
  "domain": "phrasso.com",
  "domain_verification_status": "verified"
}
```

`path` says which route the sender took: `domain` (on the verified domain) or `magic_link`. On the magic link route the response adds a `warning` noting that this sender has no DKIM.

If the address's domain isn't verified and you did **not** send the flag:

**Response** `422 Unprocessable Entity`

```json
{
  "error": "Domain phrasso.com is not verified. Register the domain or send allow_unauthenticated: true to verify the address by magic link.",
  "code": "DOMAIN_NOT_VERIFIED",
  "error_code": "DOMAIN_NOT_VERIFIED",
  "domain": "phrasso.com",
  "verification_status": "pending"
}
```

`verification_status` comes back `null` when the domain isn't even registered.

With `allow_unauthenticated: true` a verification email is sent to the address and the sender is created with `sender_source: "magic_link"`, `domain_authenticated: false` and `email_verified: false` until the recipient clicks.

<Note>
  **The verified-domain requirement belongs only to this endpoint.** [`POST /domains/verify-email`](/en/api-reference/domains#post-domainsverify-email) and the rest of `/domains/*`, called with the client's API key, work exactly as before: they don't ask for the flag and don't return `DOMAIN_NOT_VERIFIED`.
</Note>

<Warning>
  **The magic link is the exception, not the shortcut.** It verifies the mailbox, not the domain: SES signs with `d=amazonses.com`, so DKIM is never aligned with the client's domain. Use it only when the client doesn't control their DNS, and never for volume. See [Before you send volume](#before-you-send-volume).
</Warning>

## Before you send volume

**Register the client's domain before the first large send.** This isn't a hygiene recommendation: it's the difference between reaching the inbox and not reaching it.

A sender verified by email only (magic link) goes out signed with the platform's shared domain. The result, measured on real clients:

- **Microsoft rejects with `5.7.515`.** It sees `SPF=Pass, DKIM=Pass, DMARC=Fail` because nothing is aligned with the `From` domain, and it cuts off volume senders right there.
- **Gmail answers `550-5.7.1 "likely unsolicited mail"`.** Without its own DKIM, the client's reputation is mixed with everyone else sending unauthenticated.
- **No reply domain and no tracking domain.** Both hang off the verified domain.

None of this shows up as an error in your integration: the API returns `200`, the email "sends", and the problem surfaces weeks later in the bounce rate.

<Steps>
  <Step title="Create the client with their domain">
    `POST /v1/partner/projects` with `domain` and `sender`. The DNS pack comes back in the response.
  </Step>
  <Step title="Forward the verification_url">
    A public page with the records and a verify button. It's the only thing your end client needs to open, with no RQE account. If their DNS provider supports [Domain Connect](/en/api-reference/domains#get-domainsdomaindomain-connect), publishing is one click.
  </Step>
  <Step title="Wait for domain.verified">
    It arrives by webhook. Only then enable volume sending for that client.
  </Step>
  <Step title="Watch their health">
    `GET /v1/partner/projects/{projectId}` returns `health`. A client in `critical` with `can_send: true` is burning reputation silently.
  </Step>
</Steps>

<Warning>
  **Watch hard bounces, not total bounces.** Providers compute the suspension threshold (~5%) on **permanent** bounces; transient ones don't count. A domain can show a 12% total bounce rate and sit below 1% hard bounce.
</Warning>

## Errors

Every error response has the same shape:

```json
{
  "error": "Human-readable message.",
  "code": "MAX_PROJECTS_REACHED",
  "error_code": "MAX_PROJECTS_REACHED"
}
```

`code` and `error_code` **always carry the same value**. `error_code` is the canonical one; `code` is there for compatibility with existing integrations. Some errors add extra flat fields to the body, so you never have to parse the text.

### Error codes

| Code  | `error_code`                | Description                                                                     |
| ----- | --------------------------- | --------------------------------------------------------------------------------- |
| `400` | `MISSING_NAME`              | `name` is missing on project creation.                                            |
| `400` | `INVALID_EXTERNAL_KEY`      | `external_key` is longer than 200 characters.                                     |
| `400` | `INVALID_WEBHOOK_URL`       | `webhook_url` is not a valid URL or doesn't use HTTPS.                            |
| `400` | `INVALID_TIMEZONE`          | `timezone` is not a valid IANA timezone.                                          |
| `400` | `INVALID_COUNTRY`           | `country` is not a valid country code.                                            |
| `400` | `INVALID_PROJECT_ID`        | The `projectId` in the path is not a UUID.                                        |
| `400` | `EMPTY_PATCH`               | The `PATCH` carries no recognized field.                                          |
| `400` | `MISSING_DOMAIN`            | `domain` is missing when registering a domain.                                    |
| `400` | `INVALID_DOMAIN`            | The domain format is invalid.                                                     |
| `400` | `INVALID_SENDER`            | `sender` is not an object with `name` and `email`.                                |
| `400` | `MISSING_SENDER_NAME`       | The sender's name is missing.                                                     |
| `400` | `INVALID_SENDER_EMAIL`      | The sender's address format is invalid.                                           |
| `400` | `SENDER_REQUIRED_FOR_DOMAIN`| You sent `domain` without `sender`. They go together.                             |
| `400` | `DOMAIN_REQUIRED_FOR_SENDER`| You sent `sender` without `domain`. They go together.                             |
| `400` | `SENDER_DOMAIN_MISMATCH`    | The sender's address doesn't end in the domain you're registering.                |
| `401` | —                           | Missing or invalid partner key.                                                   |
| `404` | `NOT_FOUND`                 | The project doesn't exist in your organization. Another partner's client looks the same. |
| `404` | `DOMAIN_NOT_FOUND`          | The domain doesn't exist in that project.                                         |
| `409` | `MAX_PROJECTS_REACHED`      | You hit your quota. Carries `max_projects` and `active_projects` in the body.     |
| `409` | `PROJECT_DISABLED`          | The `external_key` on creation belongs to a disabled client. Carries `project_id`. |
| `409` | `DOMAIN_SENDER_CONFLICT`    | The domain is already tied to another verified sender.                            |
| `422` | `DOMAIN_NOT_VERIFIED`       | The sender requires a verified domain. Carries `domain` and `verification_status`. |
| `500` | `NO_OWNER`                  | Your partner organization has no owner.                                           |
| `500` | `CREATE_FAILED`             | Internal error creating the project.                                              |

<Note>
  **`PROJECT_DISABLED` only shows up on creation**, when you reuse the `external_key` of a disabled client. It carries the `project_id` so you know which one to call `/reactivate` on. A `PATCH` on a disabled client **does work**, on purpose: that way you can fix its webhook before bringing it back.
</Note>
